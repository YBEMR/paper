# 研究问题重组的候选决策与原文依据

日期：2026-10-03。阶段：重新审视研究问题的第1小目标；只形成有原文依据的候选，不确定新主线。

## 1．本轮结论与授权边界

**保留两个候选入口：请求合批与完整调度共同决定；模型／计算块驻留与执行安排共同决定。** 前者改变一次执行包含哪些请求，后者改变计算何时具备执行条件。它们在问题组织上均不同于当前“给定Stage后选择设备、工作点和起点”，但尚未证明具有新的学术贡献。

用户在比较现有正文与99—100号后，允许重新讨论此前固定的决策。本轮据此检查可开放什么、为什么值得开放、会改动哪些假设。**允许讨论不等于批准修改R86。** [86号](86_实验基础模型与假设确认总表.md)、[99号](99_端侧热约束节能联合模型骨架.md)、[100号](100_联合模型求解路线与适配边界.md)及历史结果保持原义；原计划的数据闭合与验证设计暂缓。

本轮完成条件是候选具有具体原文基座、应用理由和假设差异。没有开展实验、修改正文或程序，没有冻结输入、选定算法或以实验反例作为构想前提。

## 2．先区分已有能力与拟开放的决策

| 对象 | 目前已经有的决策 | 拟讨论的新决策 | 不能据此直接声称的贡献 |
|---|---|---|---|
| 现有R86／99号 | 固定Stage的设备、工作点、启动时刻；完整热能耗评价 | 本轮不继续增加功耗细节 | 设备、频率、时序联合本身不是新发现 |

## 4．候选A：批次形成与端侧完整请求调度

### 4.1 原框架分工与拟研究问题

**原文事实：** IceEdge把批次／执行模板构造和热频率控制分成算法1—2与算法3；这是一种已有协调系统，不是两套毫无联系的方法。[S1]

**拟讨论的问题：** 在有限已知请求中，是否将“哪些请求合批、在哪个设备及工作点执行、何时开始”共同规划，使批处理效率、各请求完整期限和热能耗采用同一安排评价？这里开放批次形成决策；不以证明IceEdge失效为前提，也不声称原文不能被扩展。

例如，同模型请求甲已完成前处理，请求乙尚需CPU前处理。可以让甲先执行，也可以等乙后合批。合批可能减少重复执行成本，但甲因此等待；批次完成后，两者仍可能争用CPU后处理。批次大小及频率又决定占用和功率轨迹。**值得共同决定的是“是否等乙、合哪些请求、以何种方式执行”，不是给原来固定时间表附加一次温度检查。** 上述是条件示例，没有假定批次越大一定越省能或更热。

### 4.2 继承、调整与可行性

| 项目 | 本轮候选定义 |
|---|---|
| 可继承 | IceEdge的兼容请求分组、profile和期限意识；S2的批量—频率响应与共同约束思路；原主线的完整请求及热能耗评价 |
| 最小开放 | 先只讨论同模型、同输入规格且后端支持的模型调用／固定计算块合批；不同时优化模型划分、精度、卸载或GPU内部多流 |
| 执行语义 | 一个批次可作为设备上的一次原子执行；不同请求保留各自前后继与完成期限。独占设备仍可执行一个批次，不要求多核组或设备内并发 |
| R86需要讨论的变化 | T1的固定原子执行对象、T4的跨请求合并边界、D1的批量响应；R3须增加合法批量支持。若打包／拆包不可忽略，须讨论S1或显式计算操作，不能默认免费 |
| 可以保持 | 有限已知释放、固定精度、全部输出、固定CPU资源、合法OPP／频率域、完整热安全目标 |
| 已有强替代 | 批量与工作点查表＋现有联合规划；按期限分组＋完整复核。它们若已足够，应直接采用，不要求新算法 |
| 不适用／无收益条件 | 没有兼容请求、后端只支持batch=1、到达稀疏、期限不允许等待，或批次效率没有优势；此时可退回逐请求执行 |
| 数据缺口 | 合法batch、相应时长／功率／内存、到达与完整期限、前后处理、组装成本、匹配热参数；GPU批量能力不证明目标NPU也支持 |

### 4.3 尚未解决的判断

S2已经把批处理与频率联合优化，IceEdge也已经处理热状态。因此，待核的差异必须落到**本地异构设备上的批次组成、完整工作流期限与热能耗如何共同决定**，不能只说“加入温度”。还需核查最接近方法是否已覆盖这一关系、离线已知请求与原在线服务的取舍是否值得。

本候选的故事比较直接：**单请求怎么运行，扩展为多个请求怎样组织成执行批次并共同运行。** 其与当前主线的距离较小，建议优先做下一阶段覆盖审查；这只是核查优先级，不是新主线确认。

## 5．候选B：模型驻留与计算执行共同安排

### 5.1 原框架分工与拟研究问题

**原文事实：** SwapNet §6为上层提供装入、执行和释放接口；示例方案以最大推理时延为目标，采用明确的并发执行与内存分配组织。原文也说明中间件可支持其他上层调度。因此这里借入的是现成的执行前提和成本接口，不声称发现作者无法处理的问题。[S3]

**拟讨论的问题：** 在端侧容量有限、模型／块并非始终驻留的条件下，是否共同决定装入、保留、释放与执行顺序和工作点，使“具备计算条件”与“何时计算”接受同一期限、温度和能耗评价？首个版本应把合法块目录固定为输入，避免同时开放块划分和所有存储策略。

例如，甲模型执行后，其权重保留可以供后续甲请求复用，但会占用乙所需空间；立即释放则可能使甲以后重新装入。提前装入乙能否隐藏等待，又取决于容量、装入资源和正在执行的计算。热约束还可能改变可允许的重叠或计算时机。**这些联系需要明确的装入功耗和资源占用才能成立；不是“加载必然发热更多”或“释放内存必然节能”。** 在共享内存SoC上，也不能虚构每种处理器都有一份独立显存。

### 5.2 继承、调整与可行性

| 项目 | 本轮候选定义 |
|---|---|
| 可继承 | SwapNet的块生命周期、容量及三类时延接口；SwapAdvisor提示可借鉴联合内存／时间线规划，具体工具须待正文核查 |
| 最小开放 | 固定合法计算块，选择装入、保留／释放时机及对应执行；不同时加入重计算、压缩、精度变化或云卸载 |
| R86需要讨论的变化 | 新增容量和驻留状态；T1／R3补充“支持但未装入不能执行”的条件；S1必须区分并显式计入核心装入／释放成本；D1及功率注热输入要覆盖这些操作 |
| 可以保持 | 已知有限请求、固定功能输出、非抢占计算、固定设备／合法OPP、完整期限和热安全；具体存储操作语义另行确认 |
| 已有强替代 | 现有内存感知调度＋合法工作点查表＋完整热复核；容量充足时全部预载；固定保留规则已经足够时不增加驻留优化 |
| 数据缺口 | 容量边界、权重／激活生命周期、装入与释放时延能量、预取并发条件、存储／CPU占用、注热归属、后端控制接口；目前没有与R86匹配的一整套数据 |
| 特别限制 | SwapNet中的释放包括解除指针关联及回收内存，不等于必然写回磁盘；其CPU亲和性设置也不能直接保证本题没有共享资源干扰 |

### 5.3 尚未解决的判断

SwapAdvisor已经直接声称联合优化算子调度、内存分配与交换；**不能再把“加载和计算一起安排”单独当作创新。** 尚待核的是端侧完整期限、工作点和热能耗是否形成明确且有实用价值的协调任务，以及NPU是否提供相容接口。论文题目可能更有端侧资源受限的辨识度，但实现与数据跨度也明显大于A。

该候选目前保留为第二选择，尤其需要防止研究重心滑向存储系统优化而弱化温度感知任务调度。

## 6．没有列为主候选的方向

**Stage划分与热调度：暂不重启。** ADMS的离线划分参数与在线资源调度提供了具体边界，但Band等已有子图选择；[09号](09_子图粒度候选复核与降级结论.md)还记录过热管理与计算粒度的直接近邻。旧记录不是永久否决，更不是要求先跑实验；只是本轮没有找到足以区别于这些已有能力的更清楚关系。因此不把它凑成第三个候选。

**动态精度／提前退出、跨场景部署、在线未知到达、可变CPU核组：本轮不展开。** 它们改变功能、信息或资源语义，不能因用户允许讨论假设就全部恢复。NeuOS、Phoenix的已知能力仅作为避免重复提出宽泛组合的线索，不据本轮有限阅读宣布这些问题全部解决。

## 7．本阶段完成情况与唯一下一小目标

| 检查项 | 结果 |
|---|---|
| 是否仍只是让原功耗模型更细？ | 否。A开放批次形成，B开放驻留生命周期；都改变可规划对象或执行前提 |
| 是否已有成熟原文基座？ | 是。A定位IceEdge算法分工；B定位SwapNet §6接口和示例政策 |
| 是否已经证明新颖性或收益？ | 否。已发现直接联合近邻，必须保留它们已有能力 |
| 是否需要现在做实验找旧方法失败？ | 不需要。本阶段靠应用、原文决策与范围比较提出构想 |
| 是否已经修改R86或确定论文贡献？ | 没有。候选仅供后续覆盖及可行性审查 |
| 是否要求用户下载新全文？ | 当前两个主要基座均可读；SwapAdvisor正文访问未成功，若下一阶段保留B，再补该缺口，不妨碍本轮交付 |

**唯一下一小目标：对A、B做同尺度的“已有覆盖—最小新关系—必要数据—范围代价”核查，形成一次二选一的依据。** 优先查A，B保留对照；不同时发展两套模型，不恢复原实验计划。若仅剩常规适配，也如实报告，不强行给某个候选冠以创新名称。
