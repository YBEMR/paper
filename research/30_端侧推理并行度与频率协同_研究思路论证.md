# 端侧推理并行度与频率协同：研究思路论证

范围更新（2026-09-24）：用户确认可变核组保留但暂不展开。当前主线采用[41号固定执行单元对象](41_主线研究对象与固定执行单元边界.md)，比较Stage映射、合法频率与时序；本文核数／宽度选择部分留作历史扩展，不自动进入后续建模。35–40号也未验证多CPU单元映射／并发。

日期：2026-09-23。承接[29号首选](29_结合效率刻画的研究主线再探索.md)及用户确认的端侧推理范围。本轮交付问题论证，不写完整优化模型或算法流程，不运行仿真、不预填性能收益。

**判断：该构思提供了连贯的问题解释，但尚未证明可调核数是需要保留的核心研究维度。“局部加速收益与完整推理请求收益不同”同样存在于已有映射调度中，不能直接作为新增关系。当前将并行度保留为可选建模维度，先明确相对固定核组模型增加了什么可行安排、相对已有多模式调度还需解决什么；不由配置数量增加直接推出新模型或新算法贡献。**

## 1. 可以怎样向导师说明

端侧设备上的多个推理请求共享CPU核和NPU。CPU阶段可以采用不同的并行度与频率，但增加核数、提高频率带来的加速因任务而异；阶段提前完成也不一定让整个请求提前完成，因为它还受到NPU排队及后续依赖限制。同时，不同执行模式形成不同的功率时序，影响后续热可行性。因此，希望研究任务相关执行效率下，CPU资源配置与CPU–NPU调度怎样协同，在完成相同工作量、满足期限和温度约束的前提下降低系统能耗。模型章节回答这些关系如何统一表达和比较；方法章节研究如何利用执行模式结构与瓶颈信息降低求解成本。

**建议问题表述：端侧多请求推理中，如何根据任务对CPU并行度与频率的实际响应，协调执行模式和CPU–NPU时序，实现温度与期限约束下的节能运行？**

“实际响应”表示应与选定实现相符，可以来自测量、公开数据或声明的抽象模型；当前没有硬件，不把它写成我们已经测得的真实响应。

## 2. 研究对象必须是真正的端侧推理

推荐对象是单台多核CPU–NPU端侧设备上的多请求/多模型推理，阶段DAG来自预先合法的执行划分。CPU阶段可以是CPU执行的DNN子图，也可以是有依据的前后处理；NPU阶段是可提交执行的推理子图或整个模型。不限固定两阶段，不研究任意算子切分或改变精度。

这里优先寻找**CPU确实承担可并行推理计算的混合执行任务**，而不是默认“CPU做一点前处理、全部有效计算在NPU”。若只有短小串行CPU阶段，核数配置的研究空间就不足，不能靠放大其合成耗时补出故事。

| 关系 | 现有依据 | 仍然不能推出什么 |
|---|---|---|
| 端侧请求可由不同处理器上的合法子图组成 | [Band，MobiSys 2022](../papers/2022_Jeong_Band.pdf)处理子图、设备支持集合及CPU fallback | 不是所有算子都可CPU/NPU互换，也没有证明fallback一定适合多核加速 |
| CPU任务内并行和跨请求并行存在取舍 | [OpenVINO官方CPU实现说明](https://docs.openvino.ai/2026/openvino-workflow/running-inference/optimize-inference/optimizing-low-level-implementation.html)讨论全核同步开销与streams核分组 | 不能直接给出本平台各阶段的核数—频率—功耗表 |
| 移动DNN的多核加速确受执行方式影响 | 新核到[SANI，OSDI 2026](https://www.usenix.org/system/files/osdi26-sang.pdf)，§1–2.1说明异构核间负载不均衡及算子实现匹配 | 增加LITTLE核的特定退化，不等于同类核增加也必然退化；不将其内核改造当成MATLAB已实现能力 |
| 各任务升频收益不同 | [Da Costa 2025核查](28_CPU响应模型与CoDVFS全文核查及接口方案.md)，刚性/频率敏感时间分解 | α不是可并行比例，服务器参数不能当端侧子图参数 |

因此，现实机制已有依据，**具体工作负载与合法模式仍待落实**。这与“方向没有价值”是不同的判断。

## 3. 核心矛盾：局部快，不等于系统值得加速

### 3.1 简单响应会在哪些地方影响决策

若总按核数和频率成比例估计加速，会把资源投向实际已接近饱和的阶段；若各阶段只选单独最低能耗配置，又可能忽略占用核的时间、其他请求等待及后续NPU阻塞。两种简化均可作为对照，但不能概括所有已有调度方法都如此。

少量公式足以说明第一层差异。沿用已核对CPU频率模型，在固定核组和实现下，频率从x_L提高到x_H，阶段节省时间为：

\[
\Delta d_i=D_i\alpha_i(1/x_L-1/x_H),\quad x_H>x_L>0.
\]

这是原响应式的代数推论，不是新定理。相同频率变化对不同阶段的收益与D_iα_i有关，不能只比较α_i，更不能默认都按同一加速比例缩短。核数维度还需要独立的d_i(k,f)依据，不将Amdahl函数与上述函数直接相乘当事实。

### 3.2 一个不需要调参的端到端解释

考虑一个CPU阶段完成后才可执行的NPU阶段。暂时固定NPU顺序、频率和热条件；设CPU完成时刻为c，NPU在u时刻可用，交接耗时h固定，NPU服务时长为d_N，则：

\[
C_N=\max\{c+h,u\}+d_N.
\]

- 当c+h>u，缩短CPU阶段可能使NPU更早启动。
- 当c+h<u，进一步提前CPU完成不会改变这里的NPU完成时刻。
- 跨越c+h=u后，原本有价值的加速会进入排队等待，端到端收益发生转折。

这是固定其他安排下的局部关系。多前驱、重排、交接占用或热约束变化时必须扩展，不能将它当完整调度公式。它也不证明放慢CPU必然节能：是否省能要用功率与统一时域评价。

**效率函数决定“能加速多少”；任务在整个调度中的位置决定“这段加速值不值得”。** 这就是模型刻画与任务调度的连接点。

### 3.3 核数使问题从调频进一步变成资源安排

四个CPU核可集中处理一个阶段，也可两两处理两个独立就绪阶段。增加核数不仅改变一个时长，还改变其他阶段能否同时启动。阶段从四核换到两核后，即使自身稍慢，释放的核可能推进另一请求；也可能因为NPU已经拥挤而没有端到端收益。

“核数×时长”可以描述占用量的一部分，但不能单独决定调度优劣：连续四核占用与分散的两核占用，资源可放入的时间区间不同；共享频率域还使两个并行阶段不能各自随意选频。

这可以描述为在合法执行模式之间选择资源规模，并同时安排执行，但已有多模式资源调度也能表达这种选择。若所有阶段的核数固定，并行度选择这一维度消失；任务相关频率响应、CPU–NPU依赖与热约束仍然可以研究，不能据此说整个问题失去价值。

### 3.4 新增配置不等于新增研究关系（2026-09-23修正）

相对“每个阶段占用一个不可分割CPU worker或NPU”的受限模型，可调核组增加的是：**阶段的执行模式同时决定自身时长与它排斥哪些并发执行，而不是只决定在哪个处理器上运行。** 非比例加速使占用更多核与节省时间之间不能按等比例折算。

例如四核中，A可占用{1,2}或{1,2,3,4}，B可占用{3,4}。A选两核时可与B重叠，选四核时必须与B错开；若B完成后有NPU阶段，A的核组选择还能改变该阶段的就绪时刻。这仅说明可行安排的区别。没有时长、功率、期限和热参数，不能判定哪种安排能耗更低，更不能声称已经改变了真实实例的系统最优解。

**表达能力边界：** 若把上述核组当成彼此独立的虚拟处理器，会遗漏重叠核组的资源冲突；但为每种模式登记实际核集合、时间/功率并加上逐核互斥后，已有多模式映射/资源调度框架就可以表达。对可互换的同类核，也可能用容量约束表达；异构核或不同热位置不能只按核数等同处理。因此不能笼统说“以前CPU/NPU子图映射无法表达”。应逐篇核对其资源与模式定义。

这种核数分配与非线性加速关系本身也已有研究。Crown 2019 §III-A联合选择并行宽度、核组与频率，§II-A在稳态轮次内将任务实例按独立任务处理。它可作为方法工具及近邻，不能据其特定假设断言全部已有工作都缺少依赖处理。

当前真正待论证的是：**在代表性端侧推理流程中，固定CPU核组或先独立定核组的简化，会不会错配任务内与任务间并行机会，并通过NPU就绪及热历史改变节能配置的选择？已有多模式联合调度需要怎样适配，适配后的实质工作在哪里？** 这是候选问题，不是已证实缺口。无需追求旧框架在数学上绝对无法表达，也不要求所有简单方法失败；但必须交代具体适配或求解内容，不能以多加1/2/4核选项代替论证。

## 4. 温度为什么是问题的一部分

CPU与NPU通过任务依赖相连，还可能通过芯片/封装热耦合相互影响。核数、频率、并行重叠和执行时长共同改变功率轨迹；温度又限制哪些后续模式可行。即使跨节点耦合较弱，每个资源自身的热历史也可能影响后续执行，但不能因此假设CPU必定显著加热NPU。

```mermaid
flowchart LR
    A[阶段对核数和频率的响应] --> B[选择合法执行模式]
    B --> C[时长与核组占用]
    C --> D[CPU完成顺序与NPU启动]
    B --> E[功率与热轨迹]
    D --> E
    E --> F[后续模式的热可行性]
    F --> B
    D --> G[完整请求期限与系统能耗]
    E --> G
```

本图表达拟研究关系，不代表任何方向已测得收益。温度必须经功率和热状态推进，不能额外发明一个“越热效率指数下降”的函数，也不能把热余量当成静态功率配额。

需要分别评价两个影响：

1. **资源影响：** 同一CPU总资源在任务内集中与任务间分配时，DAG完成时间不同。
2. **热影响：** 即使资源/期限可行，不同模式和重叠安排的全过程温度也可能不同，进而改变可用配置。

热约束不活跃时仍可能有并行度优化价值，但不能把这部分全部归因于温度。固定配置、固定工作量和固定时域功耗规则下，单改顺序也未必降低能耗；需交代它是否允许选择另一组更节能模式。

## 5. 多篇方法结合时，具体需要补什么

| 方法来源 | 可借用部分 | 接入本问题的适配工作 |
|---|---|---|
| CPU/NPU性能响应 | 合法配置下的时间和功率关系 | 从整机/算子原范围落到阶段模式，区分频率、核组、设备；限定参数有效域 |
| Crown类核组调度 | 多核同时占用、核组候选和搜索空间组织 | 处理CPU–NPU阶段依赖与不同就绪时间；核组/次序限制是基线选择，不直接继承最优性 |
| Band类子图调度 | 合法处理器集合、依赖与交接 | 本轮固定合法划分；若调CPU并行度，要另定义每个子图可用核组及功耗，不能把worker数量当子图内部线程数 |
| 既有热评价/控制 | 热状态推进与完整执行区间检查 | 将预测约束用于模式评价；若等待/改配置，需重新检验后续期限和资源 |

重要近邻边界：

- Crown 2019已联合核数、频率和任务类型，§III-A/B通过并行效率表达核数响应；共享调频域也已有2016工作。不能把这些决策组合称为全新。
- Band §4.1允许配置worker数量，§6.1实验设置两个单线程CPU worker；这是具体实现/实验范围，**不证明Band原则上不能扩展多核子图**。其相关工作还讨论了向多worker子图执行扩展的可能。
- Band §4.3已有热不可用后的worker禁用与重新入队机制。我们的候选是预测热轨迹下的能耗与模式协同，不能称“给完全不管温度的Band首次加温度”。
- SANI处理算子内部的异构核执行匹配；我们拟研究阶段级资源选择与跨设备时序。其内部优化可以影响响应数据，不需为了使用其结果重做一套Arm-CL内核。

**我们希望贡献的是同一评价标准下的模式选择与调度协调。** 若最后只是给成熟核组调度器换一张表，加一次普通热检查，增量工作可能偏薄；若形成模式评价、可行性保持和结构化求解的一致方法，才有更完整的研究内容。此处是贡献计划，不是全领域空白结论。

## 6. 为什么值得联合，但不预设简单方法失败

| 方法层次 | 能解决什么 | 在本研究中的角色 |
|---|---|---|
| 逐阶段独立最低能耗模式 | 忽略其他任务时的局部选择 | 检查系统协调是否必要的对照 |
| 完整模式表＋现有调度器 | 固定模式或逐次尝试模式后安排时序 | 合理直接组合；若效果足够，可成为最终方法 |
| 核组/配置选择后加等待与局部修复 | 可消除一部分热冲突和失约 | 必须保留，不能用很弱贪心制造优势 |
| 对所有模式与时序完整联合搜索 | 在声明搜索空间内求参照解 | 小规模质量基准；不能预先断言一定很慢 |
| 利用响应和瓶颈信息的协调搜索 | 希望少评估无效调整、更快找到优质可行解 | 拟研究的方法工作，收益待验证 |

非线性响应若只是有限配置表，求解器仍可用离散时间/功率常数。模型类是否改变不是论证重点。算法可利用的是：有些加速不会改变当前瓶颈，有些模式改变会连带影响核组、域频率及后续热状态；怎样识别有效候选、保留必要选择、控制评价成本，是明确的方法问题。

不能默认“时长更长、能耗更高”的模式一定可删，因为它可能有较低瞬时功率或不同资源占用。任何安全删减应有适用条件；否则只能称启发式限制，并保留回退/无删减对照。

## 7. 两章怎样衔接，工作量来自哪里

这里仅说明两章各自要回答的问题，不展开完整符号表、求解伪代码或实现任务。

| 拟议章节 | 要回答的问题 | 实质产出 |
|---|---|---|
| 第三章：任务相关执行模式下的热约束协同调度 | 怎样比较核数、频率和CPU/NPU安排，使时间、能耗和热评价一致？局部最优模式何时失去系统优势？ | 合法模式与响应适配；资源/期限/热联合表达；参照求解；模式变化与决策变化的解释 |
| 第四章：利用模式响应与调度瓶颈的高效求解 | 不穷举所有组合时，怎样把计算用于更有价值的模式和重排，保持可行性并接近参照解？ | 有条件的候选简化；联动调整的评价范围；修复与质量/耗时比较；组件作用分析 |

借鉴师兄的是“同一问题的统一表达与高效求解”递进，依据[21号复盘](21_师兄论文研究链条复盘.md)，并非必须先MILP后新命名启发式。方法章不自动引入随机到达、精度选择或强化学习以增加工作量。

若后续规模实验显示完整枚举已经很便宜，第四章的计算效率主张需要缩小或调整。现在保留这项可检验主张即可，不需提前证明枚举必败。

## 8. 当前成立程度与下一步

| 层次 | 当前判断 |
|---|---|
| 现实性 | 已有端侧异构推理、CPU并行执行差异与任务相关频率响应依据 |
| 逻辑联系 | 核组占用、NPU就绪/排队、共享域及热历史能构成同一协调问题；固定后缀的max关系可直接解释局部/端到端收益差异 |
| 特定任务的适用性 | 未完成：需要确认代表性DAG中CPU阶段的并行能力、工作量占比和合法运行配置 |
| 必须使用新算法 | 未证明，也不作为本轮构思通过条件 |
| 仿真可行性 | 合法模式表＋DAG＋热状态可在MATLAB表达；同平台实测参数仍未齐备，只能先计划条件性抽象验证 |
| 论文增量贡献与收益 | 待后续近邻对照与实验分别确认 |

不宜把“CPU核数很重要”当普遍事实。如果代表性任务几乎都由NPU执行且CPU不可并行，应撤掉核数主张，回到有依据的执行模式选择；如果资源很宽裕、热限制不活跃，简单方法应表现良好。保留这些情形有助于限定结论，不意味着现在就否决候选。

**下一步先明确模型表达边界，同时补工作负载依据：** 对照固定worker映射、带核集合/容量约束的多模式映射，以及已有核组调度，说明哪些区别只是模式表扩展，哪些需要依赖与热评价适配。再从现有Band及端侧推理材料找1–2种实际流程，列清阶段、可用核组/频率、交接成本、参数来源和缺项。CPU内部并行与多个单线程worker必须分开。可调核数保留为可选维度，不预设其成为核心创新；完整模型、算法流程及实验继续暂缓。
