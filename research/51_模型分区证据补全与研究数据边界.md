# 51．模型分区证据补全与研究数据边界

日期：2026-09-25。本轮只补50号的模型—设备分区证据，不运行Android、推理、MATLAB或新仿真。历史实验和冻结参数不变。

## 1．结论：找到可追溯的后续版本分区，可以具体定义任务结构

**图6原始模型身份仍未闭合，但发现了同一作者仓库中更具体的EfficientDet-Lite0分区记录。** PR #226公开模型名、算子分组和CPU／NPU支持情况；其固定提交中的模型与50号下载文件逐字节对应。静态读取该文件可补全跨Stage张量依赖。

因此，本轮推荐的唯一代表对象为：**Band PR #226所记录的EfficientDet-Lite0模型及其条件性支持集合**。明确换用有版本依据的后续工件，**不称为2022年论文图6复现**。该对象可以形成具体的四Stage划分，不能直接形成匹配的性能／功率参数包。

研究证据等级正式登记为：

> **真实模型工件＋作者报告的分区支持＋本研究静态依赖核验；数值模式表与热平台仍为L3。**

这比仅从时间线借用“真实执行语义”更具体，但仍不是L1／L2的同平台性能标定。PR只验证分区／准备相关能力，没有提供本题完整执行时长、频率、活动功率或RC，也不能作为我们已经运行该模型的证据。

## 3．关键证据链与版本边界

### 3.1 作者报告了什么

[PR #226：Subgraph support part 1 (Partition)](https://github.com/mrsnu/band/pull/226)由仓库开发者`dostos`提交，创建于2022-12-30，合并于2023-01-11。本文固定其头提交：

`5af78b1644f77069b5f128bcc14f896cc65d8f5f`

正文说明该修改处理unit划分及合并，后续工作才处理完整调度／执行及中间张量通信。作者报告在Ubuntu及Pixel 4上检查节点数、输入输出连接和合并结果，并明确指出其结果与旧Band实现不同，原因是NNAPI版本不匹配。这里是**作者报告的分区验证语境**，不是本轮实测；正文没有逐条日志对应的系统／驱动版本、完整运行命令和原始采样记录。

对`lite-model_efficientdet_lite0_int8_1`，正文的MergeUnitSubgraph和FallbackPerWorker两段日志均列出：CPU未支持算子集合为空，NPU未支持集合为`{0,66–266}`；unit的算子组为`{0}`、`{1–65}`、`{66–265}`、`{266}`。因此，在该日志的后端条件下，CPU可准备这四组，NPU只支持第二组。该判断**不外推所有Pixel 4系统版本或所有NPU**。

日志还列出GPU／DSP支持，本文只截取CPU–NPU子集，不给其他设备设计模式。两段日志的“16 unit subgraphs”等数量含worker相关实例，不能据此把同一请求写成16个不重叠Stage；本报告用四个不重叠算子集合定义研究Stage。

### 3.2 文件是否真的对应

PR头提交的[模型路径](https://github.com/mrsnu/band/blob/5af78b1644f77069b5f128bcc14f896cc65d8f5f/band/test/data/lite-model_efficientdet_lite0_int8_1.tflite)与50号取得的当前版模型具有相同Git blob：

`8f419c65be6fb981a1aec8bffc670a236a892ba2`

本地文件按Git的`blob + 长度 + 内容`规则重新核验一致；4561184字节，SHA256为：

`33a3b622c7cac0762f96089353cd61495f3e993968d133af7871bfc2d5396704`

这一步把“同名文件”提升为**PR源树和本地工件内容一致**。输入仍为`[1,320,320,3]`、UINT8，267个算子；不能因文件名含int8而省略输入类型。PR正文中的运行日志未直接写SHA，因此这里的运行来源依赖作者对测试模型路径的说明，不能夸大为我们独立复现了设备执行。

### 3.3 CPU worker对应关系

同提交的[分区测试源码](https://github.com/mrsnu/band/blob/5af78b1644f77069b5f128bcc14f896cc65d8f5f/band/test/backend/tfl_subgraph_test.cc)第39–42行依次配置CPU、CPU、DSP、NPU、GPU；线程数分别3、4、1、1、1，CPU掩码分别BIG、LITTLE。故日志中的worker0／1为CPU，worker3为NPU。

这是**固定线程配置的两个CPU worker**，不是论文§6.1的两个单线程BIG worker，也不是44号两颗对称独占CPU核。固定多线程worker可以与41号“预先固定规模的执行单元”相容，但这不恢复可变核组决策。若后续采用两颗抽象单核单元或对称响应，必须另标L3；不得把3／4线程profile默认为单核性能。本轮没有这两种profile，也不改变主线的CPU物理配置。

测试主体检查模型创建及`RegisterModel`成功，没有调用完整请求推理并核验输出。两条评论讨论编译环境问题，未补充频点、功率或完整执行性能。因此“作者报告支持／准备成功”和“某线程模式下完成请求的实测性能”继续分开。

## 4．可采用的四Stage静态定义

以下划分沿用作者报告的四个unit边界；选择将其作为固定Stage是本研究的建模决定。固定后不再动态切分／合并，不把Band全部候选子图同时执行。

| Stage | 原模型算子ID（含端点） | 算子数 | 作者日志支持的CPU–NPU子集 | 边界性质 |
|---|---|---:|---|---|
| S0 | 0 | 1 | CPU | 不可因阶段很短而从工作量中删除 |
| S1 | 1–65 | 65 | CPU、指定NPU | 具有有来源的跨设备支持选择；不是已证NPU更快或更省电 |
| S2 | 66–265 | 200 | CPU | NPU在该记录中不支持；不补造NPU模式 |
| S3 | 266 | 1 | CPU | 产生模型最终输出；不与S2无条件合并并假装无交接 |

静态遍历模型算子的张量生产／消费关系得到：

```mermaid
flowchart LR
    I["输入张量0：1×320×320×3 UINT8"] --> S0["S0：op 0／CPU"]
    S0 -->|张量332| S1["S1：op 1–65／CPU或指定NPU"]
    S1 -->|张量390–394、396、397| S2["S2：op 66–265／CPU"]
    S2 -->|张量594、597| S3["S3：op 266／CPU"]
    S3 --> O["输出张量598–601"]
```

选择S1的NPU模式时，该版本流程为**CPU→NPU→CPU→CPU**，不再是50号图6的语义两段图，也不是旧验证的CPU→NPU两阶段。S1若选CPU，则NPU可以不参与该次请求；后续比较不能强制使用NPU来制造所谓协同收益。

静态检查覆盖267个算子恰好一次，各中间张量生产者先于消费者；跨Stage数据边只有上述三组，没有额外跨段边。无生产者且非模型输入的张量均有常量缓冲，不把权重常量误当外部任务依赖。该检查只恢复图结构，没有执行模型、分区编译或测量张量复制耗时。[静态结果](evidence_20260925/band51/stage_graph_static.json)

表中CPU支持先记为处理器类别。是否可进一步展开为`CPU₁/CPU₂ × 各合法频点`，仍须由固定占核集合、控制域、后端准备条件及本研究假设定义。算子数、张量数、文件大小均**不能直接换算成Stage时长、CPU/NPU功率或频率敏感性**。

## 5．正式接受的证据等级

| 层次 | 已有依据 | 仍缺／本研究必须显式设定 | 当前可作主张 |
|---|---|---|---|
| 工作量身份 | 固定模型工件、输入及完整算子图 | 实际输入样本、数值输出验证未执行 | 可以指认模型与结构；不能称完成端侧推理复现 |
| 固定Stage | 作者unit边界＋静态张量依赖核验 | 本研究选择固定划分；不继承全部动态候选 | 有来源的任务DAG，而非凭空四段链 |
| CPU／NPU支持 | PR记录的支持集合和分区测试配置 | 精确NNAPI／driver版本缺失，本地未复测 | 条件性采用作者报告支持，不泛化为平台普遍事实 |
| CPU执行单元 | PR中的3线程BIG／4线程LITTLE设置可追溯 | 独占核ID、频率控制域、本题选用的固定单元 | 机制与配置来源，不是两单核实测数据 |
| 模式时长与功率 | 未取得匹配测量表 | `d(i,p,f)`、活动／空闲功率、切换及交接开销 | **L3**，不得用服务器数据或旧合成结果冒充此模型profile |
| 热、到达及期限 | 有既有方法／论文规则可作设计参考 | RC、入口温度、注热边界、有限请求与期限取值 | **L3**条件性平台与工作负载；不自动继承旧实验数值 |

因此“真实执行语义＋L3模式表”现在可以更准确地表述为**结构锚定、数值抽象**。它允许研究明确假设下的配置／时序关系，不能报告真实Pixel 4节能百分比、硬期限或温度保证。没有必要再把原图6一一复现作为前置门槛，也不能把找到真实模型文件当作算法贡献已经成立。

这对硕士论文的意义是补足了“研究对象到底是什么”的一个关键环节；能否支撑整篇论文，还取决于这个对象上的具体问题、方法与强对照之间的差异、条件覆盖及学院要求。当前既不因L3否决主线，也不因多了真实任务图就保证工作量与创新性足够。

## 6．结束补证，返回主线的单一下一步

**下一步只制定该四Stage对象的条件性研究输入契约与一项主张，不立即跑实验。** 契约应明确固定CPU单元、共享频率域、S1的CPU／NPU支持、其余CPU阶段，以及哪些数值完全属于L3；不得强制S1用NPU，不改变每个请求的算子覆盖。它将决定是否需要重写当前只支持两阶段的验证器，而不是先复制旧时长／功率凑出新案例。

需要论证的单一问题为：**在这个固定DAG上，S1的设备／频率选择与前后CPU占用、请求期限及完整热轨迹结合后，现有联合规划＋完整候选后缀复核是否已经足够？** 这只是待验证的主张方向；本轮没有证明映射收益、热配置翻转或求解瓶颈。47号强基线继续保留，不另造弱对照。

停止本条补证支线，不继续追图6未公开数据，不新增论文下载任务，不构建Android环境。后续如果作者提供对应原始记录，可以提升或修正证据等级；当前工作不以它为阻塞条件。
