# K.159：P0／P1的R4只读对照分析

2026-10-22。只读取已归档R4的联动版和HEFT结果、原输入与源规则；新增求解、热评价和研究调用均为0。算法、参数、合法域、安全标准及历史记录不改，P2尚未授权或启动。

**主要结论：P0近乎持平，是两方法都找到了全L安排，活动能量和基准能量相同；P1则出现“第一阶段没有改善原高档锚，第二阶段继续锁住这些锚”的路径。P1约87.6%的能耗落后来自AC场景，主要是活动与基准项，未观察到热违规或热反馈导致这一差距。**

能耗差的数值来源、已保存局部域的限制及实际用时已经核清。第一阶段为何在P1报告零gap却未产生改善，仍不能只靠内部退出信息判定原因，不将它解释为“所有低档方案均不可行”。

## 3．工作点与最终安排发生了什么

两方法各自的设备选择模式在这两批R4中没有改变：联动的A.pre／A.main／A.post固定到CPU1／NPU0／CPU1；HEFT对应CPU2／NPU0／CPU1。两者的A.main都在NPU0，但不能把全部A部署说成相同。这里的跨场景共享是执行单元共享，不是强制所有场景共用工作点或起点。

P1的AC对照最直接，时间单位ms，结束保留原值：

| Stage | 联动：单元／工作点／起止 | HEFT：单元／工作点／起止 |
|---|---|---|
| A.pre | CPU1／L／30—50 | CPU2／L／5—25 |
| A.main | NPU0／L／50—110 | NPU0／L／25—85 |
| A.post | CPU1／L／110—120 | CPU1／L／90—100 |
| C.pre | CPU2／H／0—14.4 | CPU1／L／5—33.8 |
| C.main | GPU0／H／15—69 | GPU0／L／35—143 |
| C.post | CPU1／H／70—79.6 | CPU1／L／150—169.2 |

HEFT已保存的完整AC安排证明：在当前P1输入中，AC全L可以满足期限并保持热安全。联动最终仍为C三个Stage使用H档，不能解释为原问题要求它们全部用H。

AB中，联动为A.main选M、B.post选H，HEFT分别为L、L；两者都让B.main采用H。HEFT把B.main安排在20—48，随后A.main为50—110；联动为B.main的40—68、A.main的70—110。完整12行／方法安排、精确时长及期限见[r4_schedules.csv](r4_schedules.csv)。

### 响应变化确实改变了时序条件

两个例子可直接由已存时长表作代数核对，无需重新热评价：

1. **P0时间表不能直接沿用。** P0联动的AC中，C.post在160 ms启动，L档时长11.52 ms，171.52 ms完成，期限171.6 ms。P1同档时长变成19.2 ms，若起点仍为160 ms，结束179.2 ms，超期。P1的HEFT改为150 ms启动、169.2 ms结束，说明应重新安排，而非整个L档配置无解。
2. **AB也不能要求所有main继续用L。** 在两个main都固定到NPU0且均用L的映射下，P1时长合计60＋56＝116 ms。即使前处理使用最快档，NPU最早也只能在10 ms开始，第二个main完成下界为126 ms，已晚于两请求中较晚的125.84 ms期限，尚未计后处理。这只排除该“双L＋同NPU”组合，不排除换档、改配或整个问题。两方法都选B.main的H档具有明确时序背景。

第二例的精确必要界保存在[diagnosis.json](diagnosis.json)的`P1_AB_two_L_NPU_timing_bound`。它不是新增候选、安全见证或全问题不可行证明。

## 4．闭合锚怎样把第一阶段的结果传给第二阶段

本版不是同时开放全部Stage的OPP／起点：

- 第一阶段仅开放AB的B.main／B.post、AC的C.main／C.post；其他Stage保持初始OPP及起点，所有执行单元保持初始映射。
- 第二阶段改为开放各场景的A三个Stage和另一请求的pre；另一请求的main／post固定为第一阶段最后一个完整安全组合的选择。

这来自原`opened_stages`、`masks`与`_member`规则，源码及原冻结哈希见[source_checks.json](source_checks.json)，不是本次新增限制。

| 第二阶段闭合项 | P0的暖锚 | P1的暖锚 |
|---|---|---|
| AB B.main | L＠75 | H＠40 |
| AB B.post | L＠120 | H＠70 |
| AC C.main | L＠45 | H＠15 |
| AC C.post | L＠160 | H＠70 |

P1第一阶段没有形成新的完整改善，第二阶段暖锚与原初始安排一致。第二阶段即使还有时间，也不能把C.main的H＠15改成HEFT的L＠35，或把C.post的H＠70改成L＠150。这是已存候选域的直接限制。

成员核查确认：原HEFT安排、统一交换CPU标签后的HEFT安排，都不属于本次两阶段域；**即使暂时忽略执行单元差异，P1的第二阶段仍违反B.post、C.main、C.post的闭合工作点及相关起点**。因此，不能仅把差距归结为CPU标签。

P0的精确HEFT时间表同样不在局部域中，但其闭合项已是L档，另一套L档安排取得了近似能耗。这正是“P0几乎持平”不能外推为“固定锚在响应变化后仍足够”的原因。排除精确HEFT安排也不证明域内所有同等质量安排都不存在。

## 6．热因素与下一步边界

P1 R4的已存最终方案最高峰温上端：联动AB约51.646°C、AC约52.510°C；HEFT AB约51.308°C、AC为50°C，均低于80°C上限。没有热违规／反馈记录。温度修正能耗参与了差额，但本次没有证据表明是超温排除或反馈使联动落后。

建议将本次结论用于限定第三章方法表述：**两阶段能够改善自身初解，但第一阶段结果形成的闭合锚会影响随后能够达到的质量；响应假设变化会使这一影响显现。** 不把本次反向结果归为整个CPU／GPU／NPU热调度方向无价值，也不反向调参数寻找胜例。

P2可以作为后续热条件研究，但应保持原`initial_78`定义：**在P0/base的原H响应与其余条件上只把入口改为78°C，温限仍为80°C；不是在P1的α=1基础上再叠加高初温。** 这样才能将热条件变化与响应变化分开。下一步若推进，只先准备该条件的输入、对照与预算协议；目前没有P2执行授权，本轮未适配、预检或运行P2。
