## 二、用户提出并希望验证的两个核心问题

用户认为：即使基础实例温度上限很宽松，也可以在实验中**调整温度上限或入口温度**，验证热约束的影响；更重要的是观察本文方法是否比比较算法**更有效应对热限制**。chat主线基本赞成，并建议将两个目标分开：

1. **H1（问题作用）：** 给定相同任务、入口及物理模型，当热安全上限收紧时，哪些时间表被排除？共享部署、工作点、执行时序、等待与可行性是否受影响？
2. **H2（方法作用）：** 在**相同热条件、合法域、完整能耗目标及同预算**下，本文方法是否比HEFT/SA等比较方法更常找到SAFE方案，或在共同成功实例上取得更低完整能耗？

H1/H2都属于**待验证假设**，不是已有结论。必须严格区分“温限收紧造成的不可避免可行域收缩”与“求解不充分造成的额外能耗/失败”。算法无法消除真实温限规定的固有损失，只能在同一可行域内探索更好的安排。

还要区分：
- **热安全约束**：限制全过程温度峰值，影响可行集合。
- **温度相关漏电**：参与完整系统能耗积分；即使温限完全不活跃，也可能改变候选的能耗排序。

## 三、热压力实验的建议设计

### A. 温度上限单因素收紧——优先说明热安全约束的作用

固定场景、Stage及合法模式、释放和期限、入口温度、RC/功耗/漏电、工作点保持规则、评价窗口、权重及有限起点域，**只修改温度上限**。在模型有效温区和入口状态可行的前提下，比较宽松、临界与更严格限值。若某限值超过当前方法能力，必须区分预算内未找到、安全未决与数学上已证明无解。

K.92基准的入口为50°C、温限80°C；已得到的SAFE种子在A+B和A+C的峰温上界分别约53.13°C、52.08°C。此前对话用53°C和52°C作为**说明已有种子可能被新温限排除的概念例子**；它们**不是被批准的正式参数**，单张种子超温也不能证明该共同部署无安全时序，更不能证明原问题不可行。

同一任务和完整能耗目标下，安全集合随着最高温度上限收紧只会缩小或不变；在两个模型均有可行解、比较的是**真实最优值**时，较严格温限下的最优完整能耗不会更低。限时求得的启发式能耗曲线可能不单调，不能据此误判物理模型或数学关系。

**现有配置的 `limit_70` / `limit_90` 已经有单因素条件。** 是否另增更临界值，须事前说明选取规则、研究理由和有效域，并在正式比较前冻结，不能根据哪家算法胜出事后挑温限。

### B. 入口温度单因素变化——说明热状态影响

保持温限等其余条件，只改变各独立场景已声明的入口热状态。现有配置包含 `initial_30`、`initial_70`、`initial_78` 等条件，优先复用。

注意不同入口温度不仅改变热安全裕量，还可能改变同一安排的温度轨迹、温度相关漏电及完整能耗，因此不能把它与“只收紧温限”的结果合并解释。**当前场景入口独立，不引入跨场景温度继承或旧多模式切换。**

建议在实验协议中预先声明宽松/临界/严格类别，不用同步大幅改动热容、功率、漏电、期限与温限来制造理想效果。保留无影响、无优势或无安全方案的情形。

## 四、如何公平判断算法应对热约束的能力

方法必须对同一输入采用同样的共享具体执行单元部署规则、逐忙段DVFS、CPU共享频率域、释放与期限、5 ms启动网格及真实结束时刻、400 ms固定窗口能耗、连续四节点热安全和合法物理参数范围。所有场景（包括零权重场景）都须通过安全检查。

建议统计以下维度：

| 指标 | 目的与注意事项 |
|---|---|
| 全部实例中的预算内SAFE取得率 | 评价热限制收紧后找到可行安排的能力；失败/超时≠无解 |
| 共同成功实例上的完整加权窗口能耗 | 比较已找到的安全方案质量；不得只报告有利子集并隐去失败率 |
| 首个SAFE时间、总方法成本、构模及求解开销 | 统一计费初始构造、修复、候选评价和求解；诊断900秒不是自动冻结的正式预算 |
| 峰温与热裕量、设备映射、OPP、时间表及重叠变化 | 解释热压力怎样影响决策，而不只展示终点能量 |
| 连续违规反馈轮数、温限行与仅排除违规整表的消融 | 验证第三章反馈机制；若热违规没有触发，不能声称该反馈带来加速 |
| 完整能耗组成：活动、基准、漏电及公共项 | 区分推理执行节能、工作点保持与尾段影响 |

当前基础安全种子在A+B约81 ms、A+C约68 ms完成所有请求，评价窗口却延续至400 ms，且空闲工作点保持。长尾段可能影响完整能耗大小及排序。这是声明模型的计量规则，**不建议为追求效果而偷偷删除**；论文必须解释其影响，并将活动能耗与空闲/保持/漏电贡献分开。

现有HEFT和SA适配版本尚未作为完整正式实验方法运行；**不能预期整体MILP必然胜过它们**。第三章的MILP更适合作为完整联合模型的求解参照：在具有研究意义的小规模多场景实例争取最优性或可信界，在原规模如实报告安全U、内部界来源、超时/未决及实际成本。

## 五、当前第三章的主要困难排序

| 困难 | 事实或风险 | 本会话建议 |
|---|---|---|
| 完整MILP整数优化和界收紧困难 | K.92原规模900秒未超过SAFE种子、报告下界差距大 | 不无限追加900秒诊断；小域做可信参照，原规模做有限预算能力和局限分析 |
| 热约束作用缺少正式研究证据 | K.92默认80°C限值离已知种子峰值较远，且无热违规反馈 | 已声明的单因素热条件先作为研究性实验；明确分开温限和温度漏电作用 |
| 正式比较未闭环 | 19条件×5样本=95实例；草案675次方法调用；HEFT/SA规则及预算未完整冻结 | 先给第三章选定最低限度的正式实验与公平口径，再扩大规模 |
| 静态构模和分解归因易混淆 | K.94大量减少来自期限前置过滤，K.95/K.96新接口仅有小域验证 | 将等价期限过滤同样赋予整体MILP作为公平基线，不把它的收益算作分解独有 |
| 合成平台代表性 | CPU/GPU/NPU及耦合RC系数为文献指导的抽象/自设输入；基础任务多为三Stage串行链 | 保留抽象仿真的真实边界，不能宣称某真实SoC实测效益或一般连续起点最优 |

## 六、建议下一步及尚需主线确认的事项

**优先讨论第三章最小正式实验方案，不把实现完整精确Benders、原规模全局最优或大量新预检作为前置门槛：**

1. 选定保留至少两个有共同Stage的场景、完整热能耗与资源/频率域耦合的**研究性小域**；确认最优性和误差保证范围。
2. 明确温限与入口单因素实验的事前参数、有效域、对照场景、评价和未决口径；热条件值不由本文档自行修改。
3. 完善HEFT/SA的可执行规则及同预算定义，至少分开SAFE取得率与共同成功实例完整能耗。
4. 根据实际任务决定是否继续K.96以后固定部署单场景求解的原规模诊断；这属于**另一条求解工程路线**，不自动代替第三章实验结果。
5. 一旦实验问题、比较口径和允许的预算确定，就进入另行授权的验证，避免不断追加无结论的诊断而迟迟不能填写第三章“仿真结果与分析”。

**本纪要仅记录讨论，不授权任何修改或运行。** 后续若得到无收益或不利于本方法的结果，也应如实保留。第三章核心目标是验证模型和求解机制的作用、能力与限制；第四章是否采用分解式/混合启发另行决定。
