# E4b双请求构造失败：离线分析与最小改进建议

2026-10-26。结论：**当前卡在共享Stage层的固定贪心次序，不是热评价或构模速度。优先考虑一次期限优先构造回退，保留旧HEFT基线；暂不扩映射、扫频点或加预算。** 本轮只有已有证据的算术和源码分析，未改算法、参数，新增研究/热评价/SAFE均0。

## 1．实际发生了什么

[E4b原结果](E4_REQUESTS_EXPERIMENT_RESULTS.md)的双请求槽自然结束，四次构造都没有完整候选。其优先序完全相同：

B.pre → C.pre → B.main → C.main → A.pre → A.main → C.post → B.post → A.post。

默认/最高/中档都在A.main失败，最低档在C.main失败。单请求与双请求的保存rank值和共享Stage顺序也相同：当前rank按目录Stage计算，没有因副本翻倍而改变；随后每个Stage的两个副本整组插入。

源码定位：`heft_method.py:99`按rank选就绪Stage，`:182`按期限/ID排该Stage全部副本，`:221`没有单元可插即返回；`e1_objective/search.py:54`四次只切频点构造规则，没有改变共享Stage优先序。这里分析的是项目的共享多场景HEFT适配，不把问题归给原始HEFT论文。

## 2．设备选择为何不是首要突破口

两个同Stage副本必须共用具体单元。忽略前驱、后继及其他负载，仅看最短主阶段工作量，已有下列必要条件：

| Stage | CPU最快每份ms | 两份最少ms | 请求期限ms | CPU选择 |
|---|---:|---:|---:|---|
| A.main | 80 | 160 | 123.5 | 不可能 |
| B.main | 100 | 200 | 157.3 | 不可能 |
| C.main | 90 | 180 | 143 | 不可能 |

B.main只支持CPU/NPU，因而必须NPU；C.main只支持CPU/GPU，因而必须GPU。A.main虽然还支持GPU，但若与C共用GPU，AC场景仅四个主阶段就至少需要：

\[
2\times40+2\times45=170\text{ ms}>143\text{ ms}.
\]

所有这些主阶段必须在各请求期限前完成，而最晚期限也只有143ms，因此A.main在GPU上也不可能。**三个主阶段的必要部署实际上已压到A/B使用NPU、C使用GPU。** 这些是原完整合法域的必要条件；没有证明整体热安全可行。

所以先增加设备枚举并不对症。本例更需要协调同一NPU上A、B副本的先后关系。

## 3．固定顺序怎样把A堵住

由冻结模式表、确定的副本次序、原EFT规则及日志中的加权完成时刻和，可以推导下列已选前缀。它们不是从原日志直接读出的完整时间表，也不包括所有被拒绝单元的试探状态。

| 默认/高档前缀 | 已占用时段ms |
|---|---|
| AB中B.main/NPU | [15,50)、[50,85) |
| AC中C.main/GPU | [15,60)、[60,105) |
| 两场景A.pre/CPU2 | [0,10)、[10,20) |

A的两个主阶段最早分别在10、20ms就绪。NPU在15—85ms已经连续被B占用，前面空隙不够放一份30ms的A；两份A若从85ms开始紧接着做，至少要到：

\[
85+30+30=145\text{ ms}>123.5\text{ ms}.
\]

因此，当前固定前缀下NPU插入失败。GPU在另一个场景被C堵到105ms，A最快一份也需40ms，同样无法在123.5ms前完成。CPU又已被上一节的容量必要条件排除。共享具体单元使两场景的阻塞共同作用在A的选择上。

中档只是进一步拉长活动：B.main占NPU[20,62)、[65,107)，A.main需34ms；就绪后的前隙、中隙、尾隙都不够。低档失败更直接：C.main在CPU单份153ms已超143ms，在GPU两份至少162ms也超143ms。**这只否定该全低档构造子域，不否定原来的多频点问题。**

## 4．顺序调整有什么具体依据

冻结前已有的静态手写夹具，NPU局部次序是：

A₁.main [10,40) → A₂.main [40,70) → B₁.main [70,105) → B₂.main [105,140)。

这四个片段来自原`e4_requests/test_input_contract.py`的常量，原356项预检中的手写合法性检查已经覆盖该夹具。本轮仅以AST读取字面量、核对局部时长，没有调用夹具生成函数、重放构造或生成完整候选，也没有热评价。它提供了调整次序的具体方向，不能当作新SAFE、算法恢复成功或节能结果。

A的123.5ms期限早于C的143ms和B的157.3ms；当前rank却先给B/C占资源。因此让较紧期限的就绪Stage先获得一次构造机会，比继续统一降频更值得先检验。

## 5．只推荐一项最小后续设计

**原四次构造均未产生完整合法候选时，若根预算仍有余量，只增加一次“就绪Stage按最早关联请求期限优先、再按原rank/ID破同分”的默认EFT构造回退。**

保留依赖就绪限制、原合法模式、共享部署、每副本OPP/起点、5ms启动集合、auto-L和同一完整热安全门。规则不得硬编码A/B/C、两个副本或这张夹具；未来正式方案必须由方法在计费预算内生成，不能将手写夹具作免费初始化。

触发条件是“没有完整合法候选”，不是泛化的“没有SAFE”；后者还包括已生成候选后超温、数值未决等，本次不扩入这些情况。原冻结HEFT入口及E1—E4结果不改；新回退应是单独可识别的适配版本，不能事后替换旧基线。

| 备选 | 本次判断 |
|---|---|
| 只延长300秒预算 | 现方法四次规则已用尽；没有新动作就不会自动找到新解 |
| 继续统一降频 | 没有改次序，且全L子域已有容量矛盾 |
| 扩大主阶段设备枚举 | 必要条件已将主阶段设备压定，不优先 |
| 一次期限优先回退 | 改动最少，直接针对A期限更紧但晚构造；首选待实现 |
| 执行副本级回溯/穿插 | 也能针对阻塞，但须撤销占用并同步多场景/共享域状态；备选 |

这是常规期限信息在构造器中的适配，尚不称算法创新、热反馈改进或节能收益。若以后实施，先做小域正确性/默认分支不变检查，再另行冻结正式研究预算；不在本轮自动实现或重跑。
