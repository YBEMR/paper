Smart city applications require machine learning (ML) capabilities at the edge, for which they require edge
devices equipped with specialized processors (e.g., GPUs). However, deploying such high-end edge devices
in large numbers is challenging, particularly in regions that face infrastructure and budget constraints (e.g.,
cities lacking ubiquitous broadband) or extreme weather conditions (e.g., hot temperatures over sustained
periods of time). Hence, custom ML frameworks are necessary that can support efficient and safe consolidation
of multiple applications with diverse workloads on fewer edge servers. We present IceEdge, an inference
serving framework for CPU-GPU based edge computing servers, which isolates colocated applications using
existing container mechanisms and provides a deadline- and thermal-aware scheduler for the ML workloads.
We implement IceEdge for a Dockerized environment on NVIDIA Jetson Xavier AGX platform. IceEdge
outperforms state-of-the-art real-time inference serving frameworks Triton and DeepRT, improving the frame
drop rate by up to 15% and reducing the temperature rise by around 12°C compared to Triton inference serving
framework.

1   INTRODUCTION
A core tenet in the design and development of “smart cities” is the use of digital platforms to
monitor and maintain public infrastructure, to improve the quality of life and safety of citizens [21].
Rapid growth in sensing and edge computing hardware as well as AI-ML models for fast and
accurate processing of sensor data are key enablers. For example, health officials can be notified in
advance if a neighborhood has dangerous particulates in the air [14] and traffic rule violations can
be automatically reported before they become a menace [20, 40]. Many companies are exploring
the use of state-of-the-art reinforcement learning methods for real-time management of traffic
congestion [11–13, 42, 43].
   The recent developments in ML research has led to deployment of such powerful models on
resource constrained edge platforms [30, 31, 37]. Due to low latency and real time requirements
applications have to maintain certain Quality of service (latency frame drop rate etc) akin to
specific tasks. Modern edge computing devices with specialized processors (e.g., GPUs), such as
NVIDIA Jetson devices, have now made it possible to run low-latency ML inference even at the
edge. However, deploying such devices in large numbers is challenging. The procurement and
installation costs for such devices can comfortably exceed 500 USD per unit. In regions that face
infrastructure and budget constraints, this is hugely detrimental, particularly if each individual
smart city application requires separate dedicated edge computing platforms (e.g., for proprietary
or security reasons).
   One of the most important (often overlooked) aspect of executing ML applications on edge devices
is that it often leads to rise in platform temperature as they are not equipped with cooling facilities
like in a data-center; and ML applications being compute-heavy push these platforms to their limits.
Thermal control in the OS is oblivious to application needs, e.g., Linux’s DVFS controller may reboot
or de-throttle the device, forcing the application to be unavailable or use a low-precision model at
a critical time. On the other hand, switching off the OS thermal control is not recommended as it
affects the platform reliability.
   While several inference serving frameworks have been proposed for the cloud platforms [16,
22, 33], these frameworks cannot be directly deployed on the edge as they are optimized for
powerful server machines and prioritize throughput over real-time guarantees. The inference
serving frameworks designed for edge devices [18, 23, 45, 46, 49] have ignored isolation between
multiple tenants. NVIDIA’s Triton Inference Server [5] supports container-based isolation for
applications, but it does not allow applications to configure their predictability requirements.
Moreover, these frameworks ignore the thermal aspects of inference serving.
   This work. We present IceEdge, thermal-aware inference serving framework for CPU-GPU
based edge computing platforms that addresses the aforementioned challenges. IceEdge supports
multi-tenancy so that multiple applications can share an edge platform. IceEdge isolates co-located
applications using existing container mechanisms. Application requests (e.g., raw inputs from
sensors) are forwarded directly from the OS to the container, and then executed on the GPU. A
central, lightweight user-space controller manages the schedule of all ML inference tasks on the GPU.
The controller receives only request metadata from the OS, makes deadline-aware global scheduling
decisions, and then conveys these to the respective containers. As many edge applications are soft
real-time (where missing a deadline occasionally does not cause catastrophic failure), IceEdge’s
scheduling algorithm uses 2-way concurrency (running two models concurrently for execution)

quality-of-service. IceEdge is also thermal-aware. It does not rely on OS thermal control; instead,
its controller carefully controls the CPU-GPU clock frequencies considering both the dynamic
workload and the thermal safety constraints of the edge platform.
   In summary, IceEdge is the first deadline-, concurrency-, and thermal-aware ML inference serving
framework for the edge to the best of our knowledge. We implement IceEdge in C++ for a Dockerized
environment on the NVIDIA Jetson Xavier AGX platform [1]. We evaluate our implementation
against NVIDIA’s Triton Inference Server [5] (which comes along with the Jetson SDK and widely
used in practice) and another baseline derived from DeepRT [45] (a state-of-the-art soft real-time
inference serving framework), using both synthetic object detection workloads and production
workloads derived from an urban traffic management system [35]. IceEdge outperforms both base-
lines in terms of throughput (frames dropped for video workloads) and thermal control (temperature
profile). IceEdge reduces the frame drop rate by around 15% and 8% respectively compared to Triton
and DeepRT while reducing the temperature rise by around 12°C and 10°C respectively.

2   ICEEDGE DESIGN CHOICES
We elaborate on IceEdge’s key design goals and motivate our design choices through empirical
results. We motivate and discuss our scheduling approach directly in Section 3.
Containerized environment for multi-tenancy. Consider three applications running on an
edge device deployed at a traffic intersection: (a) traffic rule violation detection, (b) traffic density
measurement and signal control to minimize congestion, and (c) curbside parking space manage-
ment. Each of these applications would use state-of-the-art computer vision models for object
detection (e.g. to detect vehicles, number-plates, empty parking spaces) or for image classification
(e.g. to read the characters in number-plates). These computer vision models might have different
architectures and pre-trained weights, which are all proprietary information for the companies
deploying each application. Since the edge devices need to host multiple applications from poten-
tially mutually-distrusting vendors, IceEdge should isolate the applications of different vendors
to ensure confidentiality and integrity of the ML models and data, and to ensure fault isolation
between the tenants.
   Applications on the edge may be subject to several threats, such as platform compromise [17], and
direct or side-channel attacks from compromised co-tenants [24]. Mitigations [9] for such threats
require hardware support [7, 8, 27], which is not yet ubiquitous on edge CPU-GPU devices [38, 41].
Therefore, implementing strong isolation mechanisms while retaining predictable performance
characteristics for real-time inference serving workloads is a non-trivial challenge and beyond the
scope of this work.
   IceEdge relies on light-weight isolation across applications using containers. Our design choice is
inline with the state-of-the-art supported by industry-grade platforms, such as Triton [5], and is
reasonable because vendors are interested in preserving their own confidentiality and integrity,
and not attacking other tenants, which might lead to legal repercussions. Each application vendor
instantiates one or more Docker containers on the shared edge platform, and the total number of
containers are limited by the platform resources, i.e., CPU cores, RAM, and disk space.
Per-model batching and 2-way concurrency. Several prior frameworks have demonstrated the
efficacy of batching inference requests in improving inference throughput [5, 33, 45]. Given the
isolation constraints of co-located applications, IceEdge utilizes batching on a per-model basis, i.e.,
it only batches inference requests of a single tenant model.
   On the other hand, when applications attempt to schedule multiple models on GPUs concurrently,
the CUDA framework schedules the model kernels in a time-sliced manner [29]. This means that
the execution time of one model is affected by the size, number of layers, and execution time of

   Cloud-based models tend to utilize a large portion of the GPUs during their execution. Moreover,
cloud platforms can scale out GPUs to meet their workload demands. Therefore, cloud-based
inference serving frameworks can afford to not rely on concurrency for improving inference
throughput. However, as edge GPU resources are limited, we re-examine this choice of whether to
completely ignore concurrency mechanisms in IceEdge or not.
   We run multiple concurrent instances of the ResNet-18 model on NVIDIA Jetson AGX platform
with vanilla CUDA 10.1 framework. For each model, we use an input stream consisting of a camera
video feed. In each stream, frames arrive on the CPU of the platform at an average rate of 30fps,
which are sent in fixed-sized batches of 12 frames to the respective model instance on the GPU for
inference.
   We run experiments for three concurrency configurations: 1 (standalone), 2, and 4. In each
case, we measure the per-batch inference time and total throughput across all concurrent model
executions. Figure 1a shows the CDF of the inference times for the three concurrency configurations.
We observe that at concurrency 2, the mean and 95th percentile latencies increase by 21% and 44.6%
compared to standalone, however we observed that the inference throughput for concurrency 2 is
2x the standalone throughput in our experiments. We only show the CDF due to lack of space. This
shows that 2-way concurrency can help improve inference throughput while causing acceptable
impact on latency predictability. Thus, IceEdge leverages 2-way concurrency while scheduling inference
requests from multiple applications.

3   ICEEDGE SYSTEM DESIGN
Figure 3 illustrates an overview of IceEdge’s architecture on a single edge device. A device hosts
multiple Docker containers, where each container contains one pre-trained model that serves a
specific client. A client, such as a sensor or a camera, provides inputs (e.g., video frames) that
are forwarded to the respective Docker container and queued in an inference queue within the
container. A central controller runs natively on the device, which has a global view of system state,
including all the containers and their requests, as it regularly receives metadata regarding each
request from the containers over inter-processor communication. This allows isolation of models
among the containers, and at the same time allows the controller to come up with a global schedule.
 A key idea that differentiates IceEdge from prior work is that IceEdge allows limited concurrency
(up to a factor of two in this case) but explicitly controls how and when concurrent executions
are allowed. To achieve this, IceEdge relies on a profiling table, that informs its controller how
inference times vary when any two specific models or model batches are executed concurrently on
the GPU. Specifically, the profiling table starts with inference times profiled statically (in case of
concurrent execution, this is simply a sum of the two individual inference times), and is regularly
updated using measurements from more recent inferences. Such a table-driven approach may seem
intractable in cloud settings where thousands of different clients with different model types interact
with the server. However, this approach is manageable at edge, as the number of distinct clients
and models is small (e.g., under ten).

   Once IceEdge has the knowledge of all pending requests and inference profiles, it evaluates
several schedule templates, starting with the simplest one based on the earliest deadline first (EDF)
algorithm and without considering any concurrency, and then refining the template iteratively
by first improving the average batching factor, and then the average concurrency factor across all
requests. IceEdge assumes that requests from each client are assigned a fixed client-specific relative
deadline. Absolute deadlines can then be derived from the arrival time of the request and the
relative deadline. Once the controller is satisfied with a scheduling template (i.e., it cannot improve
the template any further), it splits the template into partial application-specific schedules and sends
the partial schedules to the respective Docker containers. Each application is then responsible for
executing the specific requests at the specific time as indicated by the partial schedules.
   The IceEdge controller also features a thermal control module that uses the number of pending
requests as an input and accordingly auto-scales the GPU frequency up or down. We describe the
controller design in detail below.

3.2    Thermal Control
One of the key aspects of IceEdge’s design is its thermal controller, which ensures thermal safety
while balancing application requirements. Prior systems [5, 45] use dynamic voltage and fre-
quency scaling (DVFS) to control temperature increase. However, DVFS-based solutions impact
the performance of the system [35].
   Given the insights from Section 2, IceEdge’s thermal control takes both the system temperature
and application performance requirements into account while determining the GPU frequency
levels to switch to.
   We define 𝐹𝑡𝑢𝑟𝑏𝑜 as the maximum (turbo) frequency of the device and 𝐹𝑠𝑎𝑓 𝑒 as the desired GPU
frequency which maintains the trade-off between performance and temperature. The choice of
𝐹𝑠𝑎𝑓 𝑒 is made empirically and varies among the devices. DVFS-based inference systems are found to
reach 𝐹𝑡𝑢𝑟𝑏𝑜 for even moderate workloads. IceEdge implements a proactive thermal control which
executes the workload at 𝐹𝑠𝑎𝑓 𝑒 and only switches to 𝐹𝑡𝑢𝑟𝑏𝑜 when the performance requirement is
high, akin to the presence of burst in the input frame rate in our setup.

4    IMPLEMENTATION
We implement IceEdge in C++ and deploy it on NVIDIA Jetson AGX [1], which consists of 8 CPUs
and one Volta GPU with 512 CUDA cores, and runs Ubuntu 18.04 OS. We use TVM v0.9 and LLVM
v13.0 for hardware-specific tuning and optimization [15], and CUDA 10.1 for GPU inference. The
overhead of running IceEdge controller is roughly around 13ms consisting of the computations
needed to perform EDF, batching and checking for concurrency.
   Our setup consists of multiple Docker containers, up to one per core. Application vendors launch
one or more containers. Each container hosts a particular DNN model, with different executables
tuned with TVM for different batch sizes, i.e., 1, 4, 8, and 12. This allows us to maximize the effect
of batching, at the cost of some space complexity, as the latency for inferring a batch of size 𝑏
(using a model tuned and optimized for this batch size) is typically less than 𝑏 times the latency for
inferring a single request [22]. All tuned binaries corresponding to different batch sizes of a model
reside in the same container, as they belong to the same client model and need not be isolated.
   Each container and the controller share two producer-consumer queues (respectively), which we
use for fast inter-process communication. Each container, upon receiving an input request passes
the request meta-data to the controller over their mutual producer-consumer queue. Additionally,
each container pre-processes the input data on the CPU cores or specific hardware accelerator of
the edge platform. The IceEdge controller is invoked periodically every 150 ms (this is configurable),
and consumes new pending requests from all the incoming queues. It computes partial schedules
for the pending requests and sends them to the respective containers over the respective producer-
consumer queues. If no requests are pending, the controller goes back to sleep.
   The containers do not run the inferences immediately upon receiving the partial schedules from
the controller. The controller first receives completion notifications from each container for the
requests that were issued to the GPU in the previous iteration. When the controller receives the
last completion notification, it sends a continuation message to each container. Subsequently, each
container sends the next batch of inferences on the GPU, as per the partial schedule computed by

, Vol. 1, No. 1, Article . Publication date: March 2026.

the controller. This helps handle the effect of any unexpected GPU overruns, for instance when the
inference time exceeds that predicted by the controller when coming up with the partial schedules.
Specifically, it allows the containers to drop requests even at the last moment, if the prior request
overran its duration, thereby avoiding cascading effects. This mechanism also allows IceEdge to
ensure that the GPU is used in the expected concurrency mode, and that GPU overruns do not
lead to scenarios where more than the desired number of requests are inferred concurrently on the
GPU, which may further increase the variability in response times.
   IceEdge implements the thermal control mechanism which ensures the temperature of the hard-
ware platform is maintained within ambient level. IceEdge dynamically sets the GPU frequency to
maintain the platform temperature while aiming to minimize the frame drop rate. Experiments
performed at various frequency levels on Jetson AGX platform show the trade-off between GPU
frequency, temperature, throughput, and GPU utilization (figure 1b & 2). In order to maximize per-
formance, the IceEdge thermal controller maintains the frequency at 𝐹𝑡𝑢𝑟𝑏𝑜 = 1377𝑀𝐻𝑧, resulting
in the best throughput. To control the sharp rise in temperature, the controller sets the frequency
at 𝐹𝑠𝑎𝑓 𝑒 = 1032𝑀𝐻𝑧 to maintain the temperature performance trade-off (as observed in figure 6).
This disables Linux DVFS and prevents it from interfering with IceEdge’s thermal control. Every
time IceEdge controller is invoked, it checks (i) if the total number of outstanding requests exceeds
the threshold 𝑇𝑞𝑢𝑒𝑢𝑒 = 12 (chosen based on the frame arrival rate & controller invocation period) and
(ii) whether the rise in the temperature in the last 𝑀 = 60 seconds (400 scheduling iterations of the
controller) 𝑇𝑡𝑒𝑚𝑝 is ≤ 5°C. If both (i) and (ii) hold, then the GPU clock frequency is tuned to 𝐹𝑡𝑢𝑟𝑏𝑜 ,
while as if (i) continues to hold while (ii) does not (i.e., the temperature rises by greater than 5°C,
the controller will tune the frequency to 𝐹𝑠𝑎𝑓 𝑒 until the temperature falls by 𝑇𝑡𝑒𝑚𝑝 = 5°C again.

5   EVALUATION
We evaluate IceEdge by answering five main questions.
(a) Section 5.1: What is the overhead of containerizing DNN inference on edge platforms? Does
each inference take more time in IceEdge, compared to when running on bare metal edge hardware,
as in prior work [45]?
(b) Section 5.2: With containerization for application isolation, reduced CPU-GPU clock frequencies
for thermal safety, and its novel scheduling approach, can IceEdge match the performance of
state-of-the-art inference serving frameworks Triton [5] and DeepRT [45]? How does its scheduler
design – which allows a concurrency factor of up to two and uses a deadline-aware scheduler with
dynamic batching – help reduce frame drop rates?
(c) Section 5.3: How effective is IceEdge at populating its profiling table at runtime, and how does
this help IceEdge come up with effective concurrency-aware schedules?
(d) Section 5.4: How well does IceEdge maintain platform temperature with appropriate choice
of the CPU-GPU clock frequencies and other thermal control parameters, when compared with
baselines Triton and DeepRT?
(e) Section 5.5: How well does IceEdge perform when DNN inference requests are generated based
on a real traffic density trace, a realistic workload for edge platform?

   We additionally provide a high-level overview of the existing designs and IceEdge to facilitate
understanding of the comparisons in the forthcoming sections.
a) Triton: Executes models using either static or adaptive batching, with batch sizes configured by
the user. It does not consider deadlines and does not drop frames.
b) DeepRT: Runs each model as a separate process with model-specific queues. It is deadline-aware
and can batch requests across multiple instances of the same model.

5.2    IceEdge Latency Improvement

requests until either a fixed batch size has been reached or until a configured time limit expires,
whichever occurs first. In both modes, the batch size is passed as a configuration parameter by

150 ms (which is also the scheduling interval that we use for the IceEdge controller). For DeepRT,
we maintain model specific queues instead of docker specific queues. Each NN model is run as
a process and if there are multiple instances of the same model, DeepRT batches the requests as
much as possible across them.

5.6   Sensitivity Analysis
Performance Comparision for Varying Scheduling Intervals In this section, we evaluate the
performance of different designs against IceEdge under scheduling intervals of 50, 100, 150, 200,
and 300 ms, as shown in Figure 12. With a low scheduling interval, requests are picked up sooner,
but the batching window is limited. This results in smaller batches, reduced GPU utilization, and
lower throughput. Since the system processes fewer frames within their deadlines, the number of
dropped frames increases. In contrast, with a higher scheduling interval such as 150 ms or more,
larger batches are formed, GPU utilization improves, and throughput increases. As a result, more
frames are completed before their deadlines, and the frame drop rate decreases. Note that we show
the results for the representative execution of 6 models.
Performance Comparison for Varying Deadlines In this section, we evaluate the performance
of IceEdge compared to other designs under varying deadline constraints. Shorter deadlines result in
more missed requests, as the system has less time to process each request, whereas longer deadlines
allow more requests to be completed successfully, as shown in Figure 13. This behavior highlights
the trade-off between system responsiveness and the ability to batch and process requests efficiently,
with tighter deadlines putting greater pressure on the scheduling and processing mechanisms.

Inference Scheduling in Cloud. QosSched [19] uses deep reinforcement learning (RL) to adap-
tively choose ML model and inference batch size to balance inference latency vs. accuracy. Clip-
per [16] introduces caching, batching, and adaptive ML model selection techniques to improve
latency and throughput, but it does not provide predictability for inference latencies. Clockwork [22]
reduces arbitrarily long tail latencies for ML inferences, by planning tasks ahead of time, and disal-
lowing concurrency. IceEdge is tailored for edge platforms and uses simpler scheduling heuristics
than heavy computations in RL. Unlike Clockwork, we support limited concurrency of 2 improving

platform utilization.

Inference Scheduling on the Edge. NVIDIA’s Triton Inference Server [5] does not support
dynamic batching or provide latency guarantees, limiting its effectiveness for real-time applications
that require predictable response times. DeepRT [45], like IceEdge, introduces dynamic batching
and ensures latency guarantees using Earliest Deadline First (EDF) scheduling. However, IceEdge
employs a more practical batching strategy tailored for multi-tenant environments by batching
only requests from the same application. This design choice is driven by the fact that model weights
typically differ across applications, making cross-application batching inefficient. Additionally,
IceEdge implements limited concurrency, striking a balance between maximizing throughput and
maintaining low latency, as empirically validated in our performance evaluations.
   Existing works have explored different strategies for optimizing inference performance across
heterogeneous platforms. Band [23] utilizes a variety of accelerators in mobile devices to execute
different deep neural networks (DNNs) efficiently, whereas edge platforms predominantly rely on
NVIDIA GPUs, requiring a different approach to workload management. Yi et al. [46] propose a
fine-grained scheduling mechanism by decomposing neural networks into smaller, independently
schedulable compute graphs. This approach offers greater control over resource allocation and
execution timing. In contrast, IceEdge currently schedules entire neural networks as a single unit.
If Docker containers were to partition their NNs into smaller subgraphs, IceEdge could seamlessly
integrate this capability, though it would require maintaining larger profile tables to track execution
characteristics.
   Several other frameworks focus on optimizing inference efficiency through resource sharing
and interference management. DeepQuery [18] enables the co-location of real-time (RT) and non-
real-time workloads on shared GPUs, prioritizing RT tasks while striving to maximize non-RT
task performance. Miriam [49] addresses contention in shared GPU environments by carefully
orchestrating CUDA kernel execution to minimize intra-SM and inter-SM interference among co-
located DNNs. µ-Serve [32]is a power-aware model-serving framework that combines fine-grained
model multiplexing with dynamic GPU frequency scaling. Existing techniques such as model
parallelism, placement, replication, and batching improve performance but do not exploit GPU
frequency scaling. Despite these advancements, IceEdge differentiates itself by operating within
separate Docker containers, where inference requests are strictly isolated. This design ensures
process-level security and resource separation but inherently prevents simultaneous execution of
inference requests within the shared GPU space due to process isolation constraints. By integrating
practical batching policies, controlled concurrency, and tenant-aware scheduling, IceEdge presents
a unique approach to optimizing inference performance in multi-tenant edge GPU environments.

Thermal safety at the edge. None of the papers listed above discuss thermal safety and leave
it to Linux DVFS to reboot device or scale clock frequencies in case platform temperatures rise.
EdgeEngine [6] is the framework designed with thermal aware capabilities for the edge and is
the closest to our solution. It uses RL model to make scheduling decision in-order to maintain
the platform temperature. Unlike IceEdge, EdgeEngine does consider concurrent model execution.
Also it takes into account only two operating temperatures, i.e. 20°C & 70°C while missing out
on the critical factor of looking into temperature rise due to model execution that can severely
impact the system performance. The authors in [35] present an application dynamism and ambient
temperature aware controller for Neural Network concurrency. It controls the number of threads
and frequencies on the accelerator to manage application utility under strict thermal and power
thresholds. However, it only focuses on traffic application as the use case and provides scheduling

decisions, without considering a mix of applications, each with possibly different FPS and frequency
requirements.
   Maity et al. [25, 26] address thermal management in heterogeneous MPSoCs for data-intensive
Cyber-physical Systems using an analytical thermal model and Model Predictive Control (MPC).
However, it might be impractical to profile and build analytical thermal models at different ambient
temperatures, for the heterogeneous applications on shared GPU platforms. In contrast, IceEdge
ensures thermal safety by a simpler, more practical approach of disabling DVFS and selecting
appropriate operating frequencies at runtime, based on platform temperature and input workload.
The work proposed by [39] introduce thermal-aware scheduling algorithms to optimize DNN
execution on mobile devices by balancing performance and energy efficiency between GPU and
NPU. While GPUs offer higher accuracy but cause overheating, NPUs are faster and more efficient
but less accurate. The study introduces a Heuristic-Based Scheduling (HBS) algorithm that predicts
temperature based on historical data and a Deep Reinforcement Learning Scheduling (DRLS)
algorithm that optimizes long-term performance. However, it does not address the challenge of
running multiple applications concurrently on the same hardware, as we do in IceEdge. Our work
explores the complexities of resource contention and scheduling when multiple DNN workloads
share the same GPU, ensuring fair resource allocation while maintaining optimal thermal and
performance tradeoff.
7 CONCLUSION AND FUTURE WORK
In this paper, we present the challenges of deploying ML capabilities at the edge for smart city
applications and address them with IceEdge, a novel framework for real-time inference on CPU-GPU
based edge devices. IceEdge supports multi-tenancy, enhances inference performance compared
to state-of-the-art methods, and controls platform temperatures. This allows efficient and safe
consolidation of multiple applications on fewer devices, making it ideal for smart city deployment in
regions with infrastructure constraints and extreme weather. To increase adoption, strong isolation
mechanisms must be integrated without compromising performance, and schedules must adapt to
diverse edge device types. Enabling these requirements will be the focus of our future work.
