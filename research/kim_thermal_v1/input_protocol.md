# V1 输入、固定部署与运行规则

## 输入的物理含义

这是一台四热节点的模拟设备。CPU1 与 CPU2 是两个可并行的核，合用一个工作点。GPU0 和 NPU0 各有独立工作点。A、B、C 是三种固定计算量与精度的抽象单请求推理流水线。Stage 目录对应前处理、推理、后处理。它们的功能粒度代表端侧推理，但不对应厂商实测网络。数值来源可以从 inputs.json 的路径和 SHA-256 追溯到旧配置。平台与工作量单位为 GHz、V、ms、W、°C、J/K、W/K。查表时先按预留的固定执行单元筛掉其他模式，再使用旧 inputs._expand_modes 精确展开工作点。

| 参数 | V1 取值或生成方式 | 来源与边界 |
|---|---|---|
| Stage 最高档时间、动态功率、频率敏感系数 | 读取旧目录 A/B/C 九个 Stage，样本 R1，不缩放 | 全为旧项目自设，合法性与数值来自 config_v01.json，并非 Kim、EdgeEngine 所测 |
| OPP 频率与电压 | CPU 0.8/1.6 GHz，0.70/0.90 V；GPU 0.4/0.8，0.65/0.85；NPU 0.5/1.0，0.65/0.85 | 旧配置三档的低、高两档。CPU/GPU/NPU 三个域独立取档，共八种配置 |
| 时间、动态功率 | d = d_ref (1−α+α f_ref/f)；q = q_ref (V/V_ref)²(f/f_ref) | 旧程序的频率敏感性与动态功耗近似。α 和 q_ref 为假设，未拟合某芯片 |
| 设备与部署 | A 依次 CPU1/NPU0/CPU1，B 为 CPU2/NPU0/CPU2，C 为 CPU1/GPU0/CPU2 | 自设且逐项匹配旧目录合法执行模式。应用内、跨场景均固定；GPU/NPU 共享设备时排队 |
| 温度/功率关系 | 各热节点局部线性漏电，在活动与空闲时都计算。CPU 域基准功率两节点平分，外部公共功率 0.30 W 只计入系统电能 | 四节点热容、热导、漏电斜率、基准功率全部继承旧自设配置。环境与功率参考温度同为 25°C |
| 温度入口与温限 | 首段四节点均为 50 或 78°C；各节点连续上限 80°C | 旧配置提供的初温和限值，不因结果改变。温度影响漏电与可行性；执行时长固定依赖工作点，无自动热降频 |
| 时长与频率政策 | 每段 240 ms，连续 8 段，末尾 100 ms 全低档，总窗 2.020 s | V1 自设。进入无在途工作的边界立即设置三个域的本段 OPP，整个段内空闲也保持该档；尾段切换全低。频率变更与跨设备交接的额外耗时、耗能均取零 |
| 绝对期限 | 释放时刻加上该应用在旧配置中 CPU 最高档的三阶段时间和，A/B/C 分别为 95/121/110 ms | 用旧 configs 的 beta=1.0 口径。相对期限均与本次所选工作点无关 |
| 能耗边界 | 所有工作点基准、活动增量、温度漏电及公共功率按场景与尾段分段计能 | 此处“完整”指这个模拟系统全时窗全项；存储、稳压器与传输未另行校准或逐项测量 |

## 冻结的轨迹生成规则

- 活跃集合为 AB、AC、BC、ABC。每条轨迹含每一种场景各两次。两种顺序是预先指定的混排与分组排列，顺序为 inputs.json 中的 mixed 和 grouped。只置换段，同一负载与种子下的应用、时间窗、请求和抖动逐项相同。
- 低负载每个活跃应用在一段中释放一个请求，高负载每个应用释放两个。基本释放时刻分别为 [0] 与 [0, 90] ms。每个请求加 0–8 ms 均匀整数抖动。种子为 101、202、303。每个请求从 SHA-256(种子/场景/副本序号/应用名) 的大端整数初始化 Python random.Random，使用包含两端的 randint 采样。抖动与此次选频、入口温度、轨迹位置、方法无关。同类型场景重现同组请求，种子只改变释放相位，不是独立实机样本。
- 每一负载、温度、种子组合使用两种顺序，共 24 条轨迹。单条低/高负载轨迹分别完成 18/36 个请求。段内请求标识在时间线上由段序号限定。负载不改变模型、精度、Stage 需求或单次请求的工作量。
- 进入设备调度器的事件为请求释放和 Stage 完成。事件同时时先释放已完成的执行单元并解锁后继。各空闲单元在已经就绪且部署在该单元的 Stage 中，采用最早绝对期限优先，同期限按请求 ID 字典序，执行至结束，不抢占。只要已就绪就开工，不额外等待，不做迁移。每个 Stage 的执行时间按所选档推导；所有调度时刻采用有理数，不量化到 5 ms 网格。
- 所有请求在空队列开始的一段内都推进到完成，若任何任务超期，记录实际完成与失败原因。若跨过边界，整配置不可行；未完成工作不消失，也不使用这个前缀发起下一段。只有合法前缀才可热继承。合法段末可能存在无工作的空档，仍计入热传播与电能。
- 在每一段无未完成请求的前提下，由旧 schedules._power_segments 重建执行/空闲功率事件，传入设置好的本段三个域 OPP，所有 Stage 只使用该域选择的档位。因此无任务启动过的空闲域也维持段初选择。旧第三章默认“活动时可改档、空闲保持上一实际档位”，另一控制政策为域清空后即降最低；两者都与 V1 的逐段固定控制有区别。
- 频率对执行时长与能量的具体数值以及热响应取决于假设。当前材料不提供同一真实设备上三处理器的完整功率与热导标定，不能把本实验焦耳数或安全性直接外推到手机/开发板。
