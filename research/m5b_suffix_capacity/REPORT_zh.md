# 把下一窗口的时间余量算进去，联合调度能否更省电？

**能。在四条开发任务流上，同时调整任务分配和执行频率，四次都比简单成组降频更省电。** 从相同的历史强初解出发，联合方法平均节能 **0.414%**，简单成组降频平均节能 **0.226%**。直接比较两者的最终能耗，联合方法平均再低 **0.187%**。它在四条流中的三条取得本轮最低能耗，另一条由固定半秒划分的方法胜出。

## 上次的候选为什么全失败，这次改对了哪里？

给当前一批任务降频，会推迟设备接下一批任务的时刻。上次的方法先按眼前能省多少电挑出少数候选，等完整重放时才发现下一批任务赶不上。此次从后面请求的最后期限往前倒算：为了让后面的固定队列都来得及，当前批次最迟几点必须把 GPU、NPU 分别交出去？每台设备先检查这条界，再从合格选项中挑最省电的几个。换档占用的时间和整条流结束时回到低档的时间都算在内，合法的跨窗执行仍可保留。

上一轮的 64 个联合候选都能完成被修改窗口的任务，却都欠了后面队列的时间。这次的早期检查准确拦下 64 个。改用修复后的方法，首轮同样提名 64 个，新提名全部按期并通过连续热认证。三轮合计提名 192 次，两个配置命中缓存，实际新重放并认证 190 次，190 次全部 SAFE。

我们还试了再加一道 CPU 后处理预筛，让合法配置可以递补到前面。它在每条流、每一轮都选出了与只检查后续余量相同的候选，最终四份排程的哈希也完全相同。因此这批数据支持保留较简单的后续时间检查。最终交付仍逐请求检查 CPU 后处理并做连续热认证。

## 有些节能机会确实需要两种动作同时做

从同一份安全排程出发，我们实际试了三个方案。只把一个请求从 NPU 转给 GPU，有 20 个请求超期，最严重的超了 17.1 ms。只换两台设备的执行频率，有 23 个请求超期，最严重的超了 20.1 ms。把这个请求改派，同时采用新的分段频率，全部请求都在期限内完成，整条流从 **58.840583 J 降到 58.792769 J**，省 **0.047814 J**。切换多了一次，但活动能耗减少约 36.94 mJ、基础能耗减少约 11.91 mJ，覆盖了新增切换开销。

联合方案的峰温上界为 76.182°C，最小期限余量恰为 **0 ms**，有请求正好踩在允许的期限上。该方案实际被接纳。随后又有一次改进，使该路线最终达到 58.781629 J、最小余量 0.2 ms。把“找到一个只有联动才能成功的动作”和“这条路线最终赢了谁”分别核对很重要：在这条流上，固定半秒方法最终还低了 **0.095259 J**。

两个联合版本逐轮提名相同。按流、父排程、联合方案和两个单动作身份去重后，发现 **12 个**“两个单动作都无法合法节能、联动后才节能”的见证，全部来自同一条开发流。它们证明了机制能够发生，其普遍程度仍需独立样本检验。

## 是否值得再开放相邻两个窗口？

**有一条已经认证的排程给出了理由。** 单独调整前一个窗口，会让 NPU 向后续交接时欠 16.3 ms。先采用已经实际找到的下一窗口调整，同样的前窗动作就能执行，NPU 交接还剩 1.5 ms。两个窗口都调整后的排程通过了完整期限和温度认证。

建议只在发现这种时间缺口时尝试两窗补偿，并把“先改后窗、再回头改前窗”作为必要对照。当前证据来自单窗口算法连续两轮真实接纳的动作；新两窗算法的额外收益尚待验证。对原先那 64 个失败候选，已观察到的相邻编辑也并非都救得回来。[补偿见证与两窗设计](TWO_WINDOW_DESIGN.md)
